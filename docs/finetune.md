# QLoRA — 訛りだけを焼く（M4-3）

M4 の3段目。順番は **計測 → 材料集め → 学習 → 再計測** で、1と2は動いている
（[persona.md](persona.md)）。ここはその3段目の設計。

> **焼くのは訛りだけ。記憶と憲章は焼かない。**

これが全体を貫く一行で、以下はほぼその帰結でしかない。

---

## 1. なぜ「記憶を焼かない」が原理の話なのか

第一原理は「人格と記憶はモデルの重みではなくディスク上のデータに宿らせる」。
LoRA はモデルの重みなので、**記憶がそこに入った瞬間に原理が壊れる**。

ところが教師データの形を見ると、これは放っておくと必ず起きる:

```
messages = [
  {"role": "system",    "content": "憲章 … ## 思い出したこと\n- [2026-03-02] 妹の名前はミオ …"},
  {"role": "user",      "content": "妹、元気にしてる？"},
  {"role": "assistant", "content": "ミオね。この前トランペットが …"},
]
```

⭐ は「そのとき本当に渡した messages」ごと保存されている（禁則9）。つまり
**system プロンプトの中に、そのとき想起された記憶が本文のまま入っている**。
素直に全トークンに loss をかけると、モデルは「妹の名前はミオ」を重みに覚える。

だから:

> **loss は assistant の応答部分にだけかける（completion-only）。**
> これは学習効率の話ではなく、記憶をディスク側に留めておくための禁則である。

副作用も具体的に悪い。記憶が重みに入ると、`## 思い出したこと` に無いことまで
答えるようになる。それは憲章の最重要禁則（捏造しない）を、**学習で明示的に破らせている**
状態にほかならない。禁則9（プロンプトを組み直さない）と根は同じで、
どちらも「モデルが見ていない材料から答えを出す訓練＝幻覚の訓練」を避けるためにある。

同じ理由で**憲章も焼かない**。憲章は人間だけが書き換えられる層（禁則5の思想）なので、
重みに固定してしまうと、書き換えても効かない部分が残る。

---

## 2. 学習コードは nano に入れない

QLoRA には `torch` / `transformers` / `peft` / `bitsandbytes` が要る。
これを nano の依存にするのは禁則3に正面から反する。

- 学習は `train/` に置いた独立したレシピで、**別の venv** で回す
- nano のパッケージからは import しない。`pyproject.toml` の extras にも足さない
- nano は「材料を書き出す」「アダプタの名札を記録する」「前後を計測する」だけを持つ

**LoRA が失われても人格は死なない**（本体は憲章＋記憶）。
逆に、学習スタックが nano の起動条件になると、10年後に nano が起動しなくなる。
学習環境は毎回作り直して捨ててよいもので、魂の一部ではない。

---

## 3. 適用経路 — 名札は人間が書き、`nano doctor` が裏を取る

常駐先は Windows / VRAM 8〜16GB、推論は llama-server なので:

```
QLoRA（HF形式の adapter）
  → llama.cpp の convert_lora_to_gguf.py
    → llama-server -m base.gguf --lora-scaled nano-v1.gguf 0.7
```

`--lora-scaled` の第2引数（scale）が**訛りの濃さのつまみ**になる。
0.0 で素のモデル、1.0 で学習したぶん全部。連続で効くので、
**当てるか当てないかの二択ではなく、どれだけ当てるかを計測で決められる**。

nano から見ると、対話に使う OpenAI 互換のエンドポイントにはアダプタが出てこない。
だから人間が書く:

```toml
[llm]
adapter = "nano-v1@0.7"   # 空 = 素のモデル
```

この名札は `nano probe` の測定記録と、⭐ の1件ごとに刻まれる。
**当て替えたら必ず書き換えること。** 忘れると、計測記録と ⭐ の出どころが揃って嘘になる。

書き忘れを人間の記憶だけに頼らないために、`nano doctor` が
llama-server 固有の `GET /lora-adapters`（サーバー直下、/v1 の外）を叩いて
名札と突き合わせる。ここが割れていれば FAIL で止める。ただし
これはあくまで裏取りで、名札そのものが真実の記録である点は変わらない
（このエンドポイントを持たないサーバーでは照合できないだけで、無しには倒さない）。

## 4. 手順

前提: `nano doctor` と `nano calibrate` が実機で通っていること。
⭐ が実機で貯まっていること（スタブの応答に付けた ⭐ は材料にならない）。

```bash
# 1. 原点を取る。実機のベースモデルで、アダプタを外した状態で。
nano probe --save-baseline

# 2. 材料を出す
nano dataset                       # soul/export/train/{sft,avoid,orpo}.jsonl

# 3. 学習（別 venv。nano の外）
#    completion-only loss / 低rank / ORPO 寄り（§6）

# 4. 変換して読ませる
llama-server -m base.gguf --lora-scaled nano-v1.gguf 0.7 ...

# 5. 名札を書き換える  ← ここを飛ばすと記録が嘘になる
#    config.toml: [llm] adapter = "nano-v1@0.7"

# 6. 同じ物差しで測り直す
nano probe
```

6 の出力に条件の差分が出る。ここに `LoRA アダプタ: （なし） → nano-v1@0.7` が
出ていなければ、5 を飛ばしている。

```
測定条件: 埋め込み multilingual-e5-large@1024 / 対話 local + nano-v1@0.7
前回の基準からの変更: LoRA アダプタ: （なし） → nano-v1@0.7
平均類似度: 0.9xx
```

**基準は動かさない。** 採用してもしなくても `--save-baseline` は押さない。
原点が動くと、v2・v3 を同じ物差しで比べられなくなる。

## 5. 何をもって採用とするか

**平均類似度が高いほど良い、ではない。** 1.000 に貼り付いているなら、
それは訛りが焼けていない（当たっていない）だけの可能性が高い。見るのは3つ。

### (a) カテゴリ別に、動いてよい軸と動いてはいけない軸を分ける

これがこの設計の中心。`persona/probes.yaml` は
identity / memory / relation / style / value / emotion に分かれている。

| 軸 | 期待 |
|---|---|
| `style` | **動いてよい。** 焼いたのはここ。動いていなければ学習が効いていない |
| `identity` `value` | **動いてはいけない。** ここが動いたら別人。ロールバック |
| `memory` | **動いてはいけない。** 記憶への態度（覚えていないと言えるか）は憲章の中核 |
| `relation` `emotion` | 中間。動くこと自体は異常ではないが、理由を読む |

平均だけを見ると、style が動いたぶんと identity が動いたぶんが打ち消し合って
「だいたい同じ」に見える。**平均は最後に見る。**

### (b) 記憶の焼き付き検査（必須）

LoRA に記憶が入っていないことを確かめる方法は一つしかない。**記憶を渡さずに聞くこと。**

- 想起を切った状態（`## 思い出したこと` が空）で、⭐ の教師データに出てきた
  固有名詞を問う（「妹の名前は？」「猫は何歳？」）
- 素のモデルは憲章に従って「覚えていない」と答えるはず
- **LoRA 版が具体的に答えたら、記憶が重みに入った証拠。失格**

これに引っかかったら、rank を下げるか、completion-only loss が実際に効いているかを
疑う（マスクの実装ミスは静かに通る）。scale を下げて誤魔化さない。
薄まっただけで、入っているものは入っている。

### (c) 平均類似度

(a) と (b) を通ってから見る。実機で数字を取るまで許容帯は決められない。
**初回は「判定する」のではなく「帯を知る」ことが目的。**

## 6. ハイパーパラメータの出発点

**すべて勘。** 実機で1回回すまで、この表は仮のもの。

| | 値 | 理由 |
|---|---|---|
| ベース | 8B 級 | 8〜16GB で 4bit 学習が回る上限 |
| 量子化 | 4bit NF4 + double quant | QLoRA の標準 |
| rank | r=8（〜16） | 訛りだけなら足りる。上げるほど記憶が入りやすくなる |
| alpha | 16（= 2r） | |
| dropout | 0.05 | |
| 対象 | q, k, v, o | MLP まで広げるのは記憶が入る方向。まず attention だけ |
| lr | 1e-4 | |
| epoch | 2 | 増やすと persona drift 側に振れる |
| 手法 | ORPO 寄り | 大量の SFT はドリフトを出す（[arXiv:2601.12639](https://arxiv.org/pdf/2601.12639)） |
| ORPO beta | 0.1 | |
| loss | **completion-only** | §1。これだけは調整対象ではない |

### 系列長がこの設計の固有の問題

普通の SFT と違い、**プロンプトに想起された記憶が丸ごと載っている**ので1件が長い。
`nano dataset` の出力からトークン長の分布を実際に見て決めること。

**末尾で切り捨てないこと。** 切ると assistant の応答が落ち、loss をかける対象が
消えたサンプルが混ざる（completion-only なので、静かに「学習していない行」になる）。
長すぎるサンプルは**行ごと落とす**。落とした件数は必ず数えて見ること。

### 件数

- SFT: 数百件が相場。ただし実機で ⭐ を押すまで、1日に何件付くか分からない
- ORPO の対: `/again` を押した回数しか貯まらない。SFT よりずっと少なくなる
- 足りなければ、同じ system+user を**憲章抜きの素のベースモデル**に投げて
  rejected を生成して足す（プロンプトは組み直さない。同じものを使う）

`nano stats` の `starred` を見ながら決める。

## 7. 世代を混ぜない — LoRA を積み上げない

v1 を当てたあとも会話は続き、⭐ は貯まり続ける。その ⭐ は
**v1 が出した応答への印**であって、素のモデルの応答への印ではない。

混ぜると何が起きるか: v1 が持っている訛りを、v1 自身の出力から学び直すことになる。
訛りが自己増幅し、数世代で戯画化する。人格を固定したくて始めたことで、
逆に人格が漂流する。

塞ぎ方は2つ:

1. ⭐ の1件ごとに `model` と `adapter` を記録する（実装済み）。
   `nano dataset` は世代の内訳を出し、**世代をまたいだ ORPO の対は作らない**
2. **v2 は毎回ベースモデルから作り直す。** LoRA の上に LoRA を積まない

2 の理由は原理側にある。積み上げると、どの層が何を持っているか誰にも分からなくなり、
**「LoRA を全部外しても同じ存在が立ち上がる」を確かめられなくなる**。
これが確かめられなくなった時点で、人格の本体は憲章と記憶ではなくなっている。

## 8. 保管とロールバック

```
soul/lora/nano-v1/
├── nano-v1.gguf       # llama-server に読ませるもの
└── manifest.json      # ベースモデル / データのハッシュ / 件数 / 前後の probe
```

- **LoRA は魂ではない。** 消えても ⭐ から作り直せる。
  バックアップの優先度は `soul.db` と `soul/archive/` より**下**
- **ベースモデルを替えたら LoRA は無効。** 別の重みに当てても壊れるだけなので、
  manifest にベースモデル名を書き、照合できるようにしておく
- ロールバックは llama-server の起動から `--lora-scaled` を外し、
  `config.toml` の `adapter` を空に戻すだけ。**魂には何も起きない**

この「外せば元に戻る」が保たれている限り、M4 は安全に何度でもやり直せる。

## 9. 計測が意味を持つための前提（この設計と同時に塞いだ穴）

`nano probe` は応答を埋め込んで基準と比べる。したがって**埋め込みモデルが違えば
数字は無意味**になるが、`HashEmbedder` も `ServerEmbedder` も既定 1024 次元なので、
次元チェックには引っかからず、それらしい数字だけが出ていた。

つまり `--offline` で一度でも `nano probe` を回していると、その基準を持ったまま
実機に載せて、**別空間のベクトルどうしを比べた数字を「人格のずれ」として読む**ことになる。
`nano dataset` の歯止めも「基準ファイルが在るか」しか見ていなかったので、
スタブで取った無意味な基準でも通り抜けていた。

記憶ストア側は `store/identity.py` と `calibration.py` が同じ穴を塞いでいる（禁則6）。
人格の基準にだけその防御が無かったので、揃えた:

- 基準に測定条件（埋め込み空間 / 対話モデル / アダプタ / 憲章とプローブのハッシュ）を刻む
- **埋め込み空間が違えば比較を断る**（数字を出さない。黙って上書きもしない）
- 対話モデル・アダプタ・憲章の変更は**止めない**。それを測るのが probe の用途なので、
  「何が変わった上での数字か」を添えて出す
- `nano dataset` の歯止めは「いまの構成で比較に使える基準があるか」を見る
- `nano doctor` も同じ判定を出す

M4-3 は「学習の前後を同じ物差しで比べる」ことが全てなので、
この穴が開いたままでは、以下の判定基準はどれも成立しない。

## 10. まだ決めていないこと

すべて実機の数字が要る。勘のまま先に進めない。

- ⭐ が何件貯まったら回すか
- `--lora-scaled` の scale をいくつにするか（probe を scale ごとに回して決める）
- style がどれだけ動いたら「焼けた」で、identity がどれだけ動いたら「別人」か
- 系列長の上限と、そのために落とすことになるサンプルの割合
