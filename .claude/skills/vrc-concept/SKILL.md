# 企画 (/vrc-concept)

目的: 「何を・誰に・なぜ売れるか・作れるか」をオーナーと合意し、`products/<name>/docs/concept.md` に固める。

## この段階のルール

- **コードを書かない。** 実現可能性は調査と設計で示す。
- 各論点は **提案 → 理由 → 選択肢 → 確認** の順で出し、オーナーの回答を待ってから次へ進む。
  ただし論点は 1 メッセージに最大 3 つまでまとめ、質問攻めにしない。
- 技術的制約と「この環境で検証できない部分」を先に出す。無理なものは無理と言う。
- 「カッコいい」「面白い」だけの案は出さない。必ず「誰が・いくら払うか」を添える。

## Step 1: コンセプト確認

以下を埋める。`docs/market/` に該当調査が無ければ先に `/vrc-research` を勧める。

- 商品種別: PC アプリ / Blender アドオン / 出品者向けツール / その他
- 対象ユーザー: 初心者 / 中級者 / 特定コミュニティ（VR 睡眠勢、出品者、配信者…）
- 提供体験: ユーザーの一日のどこで、何が楽になる/嬉しいか（1 段落）
- 販売形態: 有料 / 無料+支援版 / 本体+拡張。想定価格と根拠（競合価格）
- 参考作品: 既存商品とその差別化点
- 対応環境: PC VR / デスクトップ / Quest 単機（PC アプリは Quest 単機不可と明記）
- AI 製リスク: 画像・3D が必要な箇所があれば、どう回避するか

## Step 2: 技術的実現可能性

- 必要な技術要素（OSC / ログ解析 / OBS websocket / Blender API / unitypackage 解析 …）
- 各要素の一次情報 URL（公式 Docs、GitHub）。**未確認のまま「できる」と書かない**
- この環境で検証できる範囲 / できない範囲（実機・Unity・SteamVR 依存）
- 外部ツール依存（OyasumiVR、OBS など）とバージョン前提
- 失敗しやすい点（ログ形式の変更、OSC ポート競合、権限、Windows Defender の誤検知など）

## Step 3: Go / No-Go

- Go の条件: 差別化が言える、価格根拠がある、検証可能な設計にできる
- No-Go なら理由と代替案を 1 つ

## 出力

`products/<name>/docs/concept.md` に Step 1〜3 を書き、`product.toml` を `templates/` からコピーして
名前・価格・対応環境を埋める。次は `/vrc-spec`。
